# v1.4.0 Better Types

## Goal

Make Flower's type system more expressive without adding implicity, magical sugar, or back-end defined implementation.

I'm hoping this version pushes Flower to a clearer identity:

- modern in semantics
- explicit in control
- low-level when needed / asked
- experimental without becoming overly verbose / confusing
- compiler-defined rather than C-defined

## Design Image

There are three broad directions Flower could take here.

### 1. C-Adjacent Type System

This keeps types close to C:

- `null` is not a real language concept
- `union` is the only union concept
- Optional values are mostly pointer conventions
- Semantic unions do not really exist

This would make Flower feel harsher, somewhat simpler, and more backend-shaped. It is easier to lower currently, but it pushes Flower toward "C with nicer syntax," and I do *not* want that.

### 2. Semantic-Only Type System

This prioritizes language meaning:

- `null` is a real type
- `A | B | C` is the main union model
- Storage unions are hidden or de-emphasized in someway

This would make Flower feel more modern and type-rich, but at the cost of less explicit low-level usage. As much as I dislike the C-family vibe, I also do not want Flower to become just another high/low level modern language.

### 3. Split Model Type System

Storage and meaning become separate:

- `null` is still a real language value / type
- `A | B | C` is a semantic union type
- `union` remains as a raw storage / layout construct
- `?T` is sugar for `T | null`

This gives Flower both a semantic rich type system and remains in control of low-level concepts. This is my preferred direction, even if it will be more difficult to lower given the current backend.

## Core Decisions

### `null`

`null` should exist.

It should not merely be a C-pointer habit; it should be a real Flower value with real type-system meaning.

Preferred model:

- `null` is a built-in singleton value
- `null` participates in nullable / union typing
- `null` does not imply "all values are nullable by default"

### Nullable Types

Preferred syntax:

```flo
next: ?Node = null
name: ?string = null
```

Preferred meaning:

```flo
?T == T | null
```

This keeps nullability simple without needing to invent a second separate concept. This isn't written in stone, of course, and anything can change later on.

### Semantic Union Types

Preferred syntax:

```flo
value: int | string
result: int | float | double
```

These are semantic union types, not storage unions. They describe what values are valid, not how they are laid out in memory.

### Storage Unions

Preferred syntax (or, current syntax rather):

```flo
union Bits {
    i: int,
    f: float
}
```

This is for raw overlapping storage and layout control. It should remain a distint low-level construct and should not be treated as equivalent to `A | B`.

## Why This Direction Fits Flower

This direction pushes Flower toward:

- Explicit semantics
- Compiler-owned meaning
- Readable modern types
- Low-level escape hatches
- Experimentation without abandoning systems programming

It gives Flower a distinct image:
It's not a "C wrapper," and not a "high-level algebraic language," but instead a language with modern type meaning and explicit low-level power.

Flower's whole purpose has been to fill in a gap I've noticed when working with low-level and high-level languages. There's no need to have a dichotomy between explitness, low-level control power, and modern typing. Why not take the best of everything and combine it into one coherrent model?

## Feature Surface

### Type Aliases

```flo
type Size = int
type Name = string
```

Aliases should be transparent aliases, not nominally distinct newtypes. Purely syntax wrapping for developper experience and convenience.

`Size` and `int` should behave as the same type unless we later introduce a separate newtype feature (not planned, currently!).

### Nullable Values

```flo
current: ?Node = null

if current != null:
    next: @Node = current as @Node
end
```

### Semantic Unions

```flo
value: int | string = 10
value = "hello" as string
```

Ideally you wouldn't have to put `as string`, but I have no clue how this will work once I've actually implemented it, so we'll see.

### Memory Unions

```flo
union NumberBits {
    i: int,
    f: float
}
```

For now, unions will follow the same syntax as they currently do. I'm not yet sold on the `{ ... }` model, so there may come a new syntax that differs.

## Narrowing

Semantic unions require explicit narrowing.

- use `is` for checks
- use `as` for explicit casts after narrowing

This means there's no reliance on hidden backend trickery. This is the main direction I'm aiming for, but we'll see how it goes.

Example:

```flo
value: int | string

if value is string:
    s: string = value as string
end
```

For nullable values:

```flo
next: ?Node

if next != null:
    real_next: @Node = next as @Node
end
```

## Implementation Preference

### Phase 1

- Transparent type aliases
- Built-in `null`
- `?T` syntax and lowering as `T | null`

### Phase 2

- Semantic union parsing and representation
- Explicit narrowing rules with `is`
- Typecheck enforcement for `as`

### Phase 3

- Storage `union` cleanup / clarification
- Better interference in narrow, obvious contexts

## Backend Rule

C lowering must not define Flower semantics. If C is awkward, Flower semantics still come first. The backend may use temporary representations, but the surface language should ONLY reflect Flower's intended long-term model, not C's 'limitations'.

## Out of Scope

This milestone should not include:

- Hidden coercion everywhere
- Pattern matching
- Full exhaustiveness checking
- Nominal newtypes
- Backend-driven type semantics
- Magic inference-heavy union behavior

## Open Questions

These are decicions that still have yet to be decided on:

- Whether `null` can appear in non-nullable literal comparisons without an explicit cast
- Whether `if value is string` should narrow only inside the branch or also after-early return control flow
- Whether semantic unions should be anonymous only (`int | string`) or also named (`type value = int | string`) from the start

## Deferred Beyond v1.4

I'm intentionally postponing the following features so `v1.4` can finish as a coherent and clean type-system milestone instead of turning into a grab bag:

- Nullable narrowing on call results, such as `get_box().value != null`
- Nullable narrowing on subscript expressions, such as `items[i] != null`
- Implicit post-narrow extraction without explicit `as`
